  • ⚠️ containerd CRI checkpoint restore 漏洞被評為 Critical(GHSA-p7v4-vr35-mj6f) — 官方 advisory 喺 9/1 公佈,9/9 GKE 出 security bulletin (GCP-2026-061),9/10 Amazon Linux 出 ALAS2023-2026-2131 修補。問題出喺 containerd CRI 實作:由不受信任嘅 checkpoint 經 `CreateContainer` API 還原容器時,CRIU 會直接由 checkpoint 資料還原 process credentials、Linux capabilities、`no_new_privs` 同 seccomp state,完全唔會 enforce destination CRI 嘅 ContainerConfig — 攻擊者可以用一個 crafted checkpoint image 令容器以 root + full capabilities、無 seccomp 執行,而 containerd 嘅 CRI status 仲會報告「requested config」黎掩蓋真實狀態。影響版本 >= 2.1.0 < 2.2.7 同 >= 2.3.0 < 2.3.4。containerd Security AdvisoryGKE Security Bulletins
    • 修補版本係 2.2.7 同 2.3.4(做法係預設停用經 CreateContainer 嘅 checkpoint restore),而 2.4.0 會將整個功能移除
    • 想繼續用 restore 就要開新 config `enable_experimental_restore_via_create` — 但官方明講開咗就等於保留呢個漏洞,因為 CRIU 還原程序期間 containerd 根本 enforce 唔到 destination policy
    • 即時緩解:收緊 RBAC 嘅 `create pods` 權限、用 admission controller 拒收含 checkpoint 資料嘅 image、audit node log 有冇 "Found checkpoint of container"/"Restored container <id> successfully" 字樣
    • 已經由不受信任 checkpoint 還原過嘅容器,官方建議 stop → delete → recreate,唔可以只係升級 binary 就算
    呢個係典型「multi-tenant shared node 級別」嘅漏洞:只要 cluster 內有低權限用戶可以 create pod,加埋 node 開咗 checkpoint/restore,就等於繞過成個 securityContext 設計。自建 cluster 今個禮拜就應該核對 containerd 版本。

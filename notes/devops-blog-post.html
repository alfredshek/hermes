1CI/CD 核心概念 — 持續整合與交付

CI/CD 係 DevOps 嘅引擎:用自動化將「寫 code」到「上線」嘅過程標準化,令每次變更都快速、可重複、可驗證。

1.1 CI 與 CD 嘅分別

CI(持續整合)CD(持續交付 / 部署)
做啲咩每次 commit 自動 build + test自動 deploy 到環境(甚至生產)
目標問題早發現,唔好堆到 release 先爆任何 commit 都可以安全上線
產出可驗證嘅 build / artifact已部署 + 已驗證嘅環境

1.2 Pipeline 典型階段

Source → Build → Test → (Artifact) → Deploy → (Verify / Post-deploy) │ │ │ │ │ │ └─ unit / integration / e2e │ └─ compile + container image └─ git push / PR merge 觸發
  • Artifact 要 immutable:每個 build 有唯一版本號,之後唔改 — 先可以精準回滾
  • Verify 階段(smoke test / health check / canary analysis)係 CD 嘅靈魂,冇 verify 嘅 deploy 等於盲賭

1.3 分支策略

  • Trunk-based:短命 feature branch,一日內 merge 返 main → CI 首選,配合 feature flag
  • GitFlow:develop / release / hotfix 多層分支 → 大型 release 週期、嚴謹發布流程用

⚠️ 常見陷阱

「build 咗好耐,到 release 前一日先發現整合錯」= CI 冇做好。正確做法係每次 push 都跑,壞咗即刻知、即刻修。
⬆ 回到最頂

2GitHub Actions — Pipeline as Code

GitHub Actions 將 CI/CD 直接嵌入 GitHub:workflow 係 YAML 檔案,放喺 repo 入面,版本化、可 review、可重用。

2.1 Workflow 基本結構

  • 位置:.github/workflows/,一個 YAML = 一個 workflow
  • Trigger 靠 events:push / pull_request / schedule / workflow_dispatch(手動)等
  • Runner:GitHub-hosted(ubuntu / windows / macos,有月用量上限)vs self-hosted(自己機器,可食 cache、慳錢,但要自己維護 + 有安全風險)

2.2 關鍵語法

關鍵詞作用
uses引用現成 action(如 actions/checkout@v4)
run直接行 shell 指令
needsjob 之間嘅依賴(排先後)
matrix一個 job 多版本並行(如 Node 18/20/22)
concurrency防止同一個 workflow 重複跑(新 push 殺舊 job)
if / continue-on-error條件執行 / 容錯

2.3 Secrets 處理

  • 用 ${{ secrets.XXX }},設定放 repo / org settings,唔好硬編碼喺 YAML

⚠️ Fork PR 陷阱

pull_request 事件嘅 workflow 預設唔會收到 secrets(fork 可以改 workflow 偷 secret)。要畀 fork PR 用 secrets 就要 pull_request_target — 但嗰個係喺 base branch 環境跑,有 code injection 風險,要極小心。
⬆ 回到最頂

3Jenkins — 經典 CI 伺服器

Jenkins 係自托管 CI 嘅老大哥:自己裝、自己維護,plugin 生態超龐大,好多大型企業 legacy pipeline 都係佢。

3.1 架構

  • Master / Controller:排 job、管設定、派工作
  • Agents:真正執行 build / test 嘅機器,可以 scale out
  • Pipeline as Code 用 Jenkinsfile:Declarative(易讀、結構化)vs Scripted(靈活、似 Groovy code)

3.2 vs GitHub Actions

JenkinsGitHub Actions
托管自己 serverGitHub 托管(或 self-hosted)
設定UI + JenkinsfileYAML 喺 repo
生態~1800 個 plugin,乜都有Marketplace + 社群 action
維護成本高(upgrade / plugin 相容)低
整合要 plugin 先連到 GitHub原生深度整合

⚠️ 注意

Jenkins Master 單點故障 → 要 controller 備份 + agents 分散;plugin 升級前一定要喺 test 環境試,plugin 撞 plugin 係 Jenkins 最大死因。
⬆ 回到最頂

4Docker 基礎 — Image 與 Container

Docker 令「喺我部機行到」變成「喺邊度都行到」:包埋 runtime 環境,開發、測試、生產一致。

4.1 Image vs Container

  • Image = 唯讀模板,一層層疊起(每行 Dockerfile = 一層,有 cache)
  • Container = image 嘅執行實例,runtime 加一層 writable layer

4.2 Dockerfile 重點

FROM node:20-alpine ← base image(越細越好) WORKDIR /app COPY package*.json ./ RUN npm ci ← 先 copy 依賴清單再裝 → 層 cache 命中率高 COPY . . EXPOSE 3000 CMD ["node", "server.js"]
  • Multi-stage build:第一 stage 有 compiler 負責 build,最後 stage 淨係 copy artifact 出嚟 → image 由 1GB 變 100MB
  • Layer 順序要諗:COPY 嘅檔案愈少變,愈早放 → cache 命中愈高

4.3 持久化與網絡

  • Volume(docker 管理,推薦)/ Bind mount(直接 host 路徑,開發用)
  • 網絡:bridge(預設,container 互連)/ host / none
  • docker compose:一條 YAML 起 multi-container(service / network / volume 全包)
  • Registry:Docker Hub / ECR / GHCR

⚠️ 陷阱

Container 重啟之後,冇寫入 volume 嘅資料會消失 — state 一定要出嚟(volume / DB)。另外 image 要掃描漏洞 + 簽名(見 S15)。
⬆ 回到最頂

5Kubernetes 基礎 — 核心物件

K8s = 容器編排器:自動管理 container 嘅部署、scale、自我修復。

5.1 兩層架構

Control Plane Worker Nodes ├── API Server (所有操作入口) ├── kubelet (管 Pod) ├── etcd (狀態儲存) ├── kube-proxy (網絡規則) ├── Scheduler (排 Pod 去邊) └── container runtime (Docker/containerd) └── Controller Manager (修正 drift)

5.2 核心物件

物件作用
Pod最小部署單位,1+ container 共享網絡同 storage
Deployment管 ReplicaSet → 管 rollout / 回滾
Service穩定入口:ClusterIP(內部)/ NodePort / LoadBalancer
IngressL7 路由(hostname / path → service)
ConfigMap / Secret設定(非機密)/ 機密(base64 唔係加密!)
Namespace邏輯隔離
RBACRole / ClusterRole + Binding 控制權限

5.3 Probes 與自動 scale

  • liveness:container 死咗 → 重啟
  • readiness:未 ready → 唔派 traffic(rolling update 靠佢)
  • startup:慢啟動保護(唔好俾 liveness 喺啟動期誤殺)
  • HPA:CPU / memory / 自訂 metric 自動增減 Pod

⚠️ 陷阱

Pod 係 ephemeral,state 要放 volume / PVC;Secret 唔好放 ConfigMap 或者 commit 落 git。
⬆ 回到最頂

6K8s 部署策略 — Rolling 到 Canary

揀部署策略 = 喺「速度」同「風險」之間揀。

6.1 五種策略對比

策略運作Downtime風險適用
RollingUpdate逐個換 Pod無中(冇版本並存)預設,日常
Recreate停晒再起有高簡單環境 / 可接受停機
Blue-Green兩套環境,一刀切 traffic無低(回滾即刻)要即時回滾
Canary5% → 漸升無最低高風險 release
A/B按 header / 用戶分流無低測試功能、配合 service mesh

✅ 回滾

kubectl rollout undo deployment/xxx 即刻回上一版。Canary 一定要 monitor 埋 error rate 先升百分比,唔好死衝 100%。
⬆ 回到最頂

7Helm — K8s 套件管理

Helm = K8s 嘅「套件管理器」:將成個 app 嘅 K8s 資源打包成可重用、可參數化嘅 Chart。

7.1 Chart 結構

  • Chart.yaml(metadata)+ values.yaml(預設值)+ templates/(Go template 產生 YAML)
  • 指令:helm install / upgrade / rollback / uninstall
  • helm template 本地 render 驗證;helm lint 檢查格式
  • Chart 可以放 OCI registry(ECR / GHCR)

7.2 Values 覆蓋層級(由高到低)

helm upgrade -f my-values.yaml --set image.tag=v2 my-app ./chart │ │ └─ -f file ＞ --set flag ＞ values.yaml 預設

⚠️ 注意

helm upgrade 前用 helm diff plugin 睇清楚改咗啲咩;要自動回滾就加 --atomic(失敗自動 rollback)。
⬆ 回到最頂

8Terraform — 基礎設施即代碼

Terraform 用 HCL 描述「想要嘅狀態」,然後自動幫你建立 / 修改 / 刪除資源,多雲通殺。

8.1 工作流程

terraform init ← 裝 provider terraform plan ← 對比 state + 實際,預覽改動(免費睇) terraform apply ← 執行改動 terraform destroy ← 拆走所有資源
  • State 檔案係命根:記錄「我哋管緊咩資源」— 冇咗 state = 唔知邊個資源係自己嘅
  • Modules 重用邏輯;Workspaces / directory-per-env 做環境隔離

8.2 團隊使用鐵律

  • Remote state(S3 + DynamoDB lock / Terraform Cloud)→ 唔 lock 會互相 overwrite
  • 唔好 commit state 落 git(可能有 secrets,仲會撞 lock)
  • 唔好手改 state / 手動改雲端資源 → 會 drift(實際 vs state 唔啱)
  • 接管現有資源要用 terraform import,唔好「撞名重建」

8.3 vs CloudFormation

TerraformCloudFormation
雲支援多雲(AWS/Azure/GCP/…)淨係 AWS
State✅ 有 state 檔案❌ 冇(靠 stack)
生態Community provider 海量AWS 原生整合深
語言HCLYAML / JSON
⬆ 回到最頂

9Ansible — 配置管理

Ansible = 用 SSH 直接推設定嘅配置管理工具,Agentless 係佢最大賣點。

9.1 點運作

  • Agentless:經 SSH push,目標機唔使裝 agent(對比 Puppet / Chef 要 agent + pull)
  • YAML playbook:Inventory(hosts)→ Playbook → Tasks → Modules
  • 冪等(idempotent):task 重跑一百次,結果一樣 — 先可以放心自動化
  • Handlers:task 狀態 changed 先觸發(例如改咗 config 先重啟 service);Jinja2 template 做動態設定

9.2 vs Terraform(好多人撈亂)

TerraformAnsible
定位資源編排(建 / 管 infra 生命週期)配置管理(逐台執行動作)
模式聲明式 desired state逐 task 執行(有序)
典型起 VPC / EC2 / RDS裝 package、寫 config、起 service

✅ 黃金組合

Terraform 起 infra → Ansible 配置 OS 同 app — 兩者一齊用係業界標準做法。
⬆ 回到最頂

10AWS DevOps 服務總覽

AWS 有一套完整嘅原生 DevOps 服務,同第三方工具(如 Jenkins / GitHub Actions)互相競爭,視乎你幾想「鎖喺 AWS 生態」。

10.1 服務清單

服務作用
CodePipelineCI/CD 編排(Source → Build → Deploy → Approval)
CodeBuild托管 build,免 server,按用量收費
CodeDeploy部署到 EC2 / On-prem / Lambda / ECS,支援藍綠
CodeCommit托管 Git(而家新客一般建議用 GitHub/GitLab 或 CodeCatalyst)
CloudFormationIaC,聲明式模板
CDK用 TypeScript/Python 寫 code → 生成 CloudFormation
SAMServerless 簡化版(建喺 CFN 之上)

10.2 部署平台揀邊個

  • Elastic Beanstalk:PaaS,自動管容量 / health,最簡單
  • ECS:container 平台,Fargate 免管 node
  • EKS:K8s,最靈活但要自己管 control plane 成本
  • Lambda:zip 或 container image(最大 10GB)部署

⚠️ 注意

CodePipeline 一個 stage 完成後唔可以「回頭」— 例如 approval 之後想返轉頭做嘢,要拆成新 stage。

11監控與可觀測性 — SLO/SLI

可觀測性(Observability)三支柱:Metrics、Logs、Traces — 三樣齊晒先可以完整理解系統。

11.1 三支柱

支柱內容代表工具
Metrics數值趨勢(CPU、latency、error rate)Prometheus / CloudWatch
Logs事件明細(邊個 request、咩錯誤)ELK / Loki / CloudWatch Logs
Traces請求跨服務鏈路Jaeger / X-Ray / OpenTelemetry
  • Prometheus:pull 模式抓 metric + PromQL + Alertmanager
  • Grafana:dashboard,一個接晒所有 data source
  • CloudWatch:AWS 原生,alarm → SNS 通知

11.2 SLO / SLI / SLA

  • SLI:實際量度指標(例如「過去 30 日可用性 99.95%」)
  • SLO:你訂嘅目標(例如「季度可用性 ≥ 99.9%」)
  • SLA:對客合約(通常比 SLO 鬆,預留緩衝)
  • Error Budget = 1 − SLO:容錯額度,用晒就唔准 release — 將「幾時可以冒險」變成量化決策

⚠️ 警報疲勞

Alert 要 actionable:收到「DB latency 高」但唔知點做 = noise。好 alert 應該對應 SLO 或業務影響,唔係咩都 alert。
⬆ 回到最頂

12日誌與追蹤實務

分散式系統最怕「逐個 log 檔搵」 — 正確做法係集中式日誌管線。

12.1 日誌管線

App (寫 stdout) → Agent (Fluentd / Filebeat / OTel Collector) → 集中儲存 (Elasticsearch / Loki / CloudWatch Logs) → 查詢 + Dashboard (Kibana / Grafana)
  • ELK:Elasticsearch + Logstash + Kibana — 功能強、成本高
  • Loki:只 index label 唔 index 內容 — 慳好多錢,Grafana 原生整合
  • Correlation:log 加 request_id / trace_id → 先可以串起成條請求鏈

⚠️ 兩大禁忌

① 唔好寫本地檔案慢慢收 — 直接寫 stdout 俾 agent 收。② 唔好 log 機密(密碼 / token / PII) — 中央日誌係攻擊者金礦。
⬆ 回到最頂

13GitOps — Git 係唯一真相

GitOps 將 Git 變成整個系統嘅單一真相來源:cluster 嘅實際狀態會自動向 Git 收斂,一切變更都係 PR。

13.1 核心原則

  • Git 係 desired state;controller 不斷對比 Git vs cluster,唔啱就拉返齊(drift 自動修正)
  • 所有變更 = 開 PR → review → merge → 自動 sync → audit trail 完整
  • 回滾 = git revert;唔使再派 kubectl 權限俾人

13.2 兩大工具

Argo CDFlux
定位App 級 sync,UI 好用Controller 級,自動 reconciliation
特點Multi-cluster 支援好GitOps Toolkit 系列,無 Git 都可以(OCI)

⚠️ Secrets 點算

Secrets 唔可以明文入 Git → 用 Sealed Secrets(加密後可 commit)或 External Secrets Operator(連 AWS Secrets Manager / Vault,同步入 K8s Secret)。

14Secrets 管理

Secrets(密碼、token、API key)係安全最脆弱一環 — 因為開發者永遠想偷懶放喺 code 度。

14.1 主要方案

方案特點幾時用
AWS Secrets Manager自動 rotation、跨 region、收費AWS 上要自動輪換 DB 密碼
SSM Parameter Store免費、分層 path、冇 rotation輕量設定 / 細 secrets
HashiCorp Vault動態 secrets、多雲、encryption-as-a-service多雲 / 複雜權限環境
Sealed SecretsGit 可存加密 secretGitOps repo
SOPS檔案級加密(配 KMS / PGP)YAML / 設定檔加密

14.2 鐵律

  • 唔好入 git / container image / env 明文
  • Rotation 要自動;存取要最小權限
  • K8s 用 External Secrets Operator 由 Vault / Secrets Manager 同步入 cluster,唔好手動 copy

15DevSecOps — 安全左移

DevSecOps = 將安全由「release 前檢查」變成「由第一行 code 開始」。

15.1 掃描類型

類型掃咩代表工具
SAST靜態掃 source code(唔使跑)Semgrep / SonarQube
DAST動態掃運行中嘅 appOWASP ZAP
SCA依賴庫漏洞Dependabot / Trivy
Image 掃描容器 image 漏洞Trivy / Grype

15.2 供應鏈安全

  • 簽名:cosign / Sigstore — 證明 image 邊個出、冇被改
  • SBOM(cyclonedx / spdx):軟件物料清單,出事先知邊個組件要補
  • IAM 最小權限 + pipeline secrets 隔離 + artifact checksum 防篡改

⚠️ 常見錯

掃描淨係 release 前做一次 = 太遲。要入 CI,每個 PR 都掃;漏洞政策(CVSS 門檻,例如 ≥ 7 先 block)要一早定死。

16SRE 概念 — 用工程做營運

SRE(Site Reliability Engineering)= 用軟件工程方法解決營運問題,Google 起源,而家係 DevOps 嘅進化版。

16.1 核心概念

  • Toil:手動、重複、可自動化嘅營運工作 → 要持續量化 + 壓低
  • Error Budget:用 SLO 反推容錯額度 → 容許「有預算」嘅 release 風險
  • On-call:告警 → 分診 → 修復 / 升級;runbook 要寫好,新人跟得住
  • Postmortem(blameless):重大事故檢討唔怪人,淨係搵系統點改先唔會再發生

16.2 四個黃金訊號

訊號問嘅問題
Latency反應幾快?有冇慢 request 拖垮?
Traffic需求幾大?(QPS / 用戶數)
Errors失敗率幾高?(4xx / 5xx / timeout)
Saturation系統有幾「滿」?(CPU / 佇列深度)

✅ 口訣

冇 SLO 嘅系統冇辦法判斷「壞得幾嚴重」;有 error budget 先可以科學咁決定「呢次 release 搏唔搏」。
⬆ 回到最頂

1712-Factor App — 雲原生設計原則

12-Factor 係 Heroku 提出嘅 SaaS app 設計原則,而家係雲原生開發嘅共同語言 — 跟住做,app 先可以喺現代平台順滑運行同 scale。

17.1 十二條原則速覽

#原則重點
1Codebase一份 code,多個環境(dev/staging/prod 都係同一份)
2Dependencies顯式宣告,唔靠系統隱藏套件
3Config設定放環境變數,唔好入 code
4Backing servicesDB / queue 當可替換資源,唔好寫死
5Build-release-run三個階段分開,release 不可變
6Stateless processProcess 冇本地狀態,state 放外部服務
7Port bindingApp 自己聽 port,唔靠嵌入 server
8Concurrency用 process 模型 scale(唔係 thread 硬撑)
9Disposability快起快停,graceful shutdown
10Dev-prod parity開發 / 生產環境愈似愈好
11LogsLog 當 event stream,寫 stdout
12Admin tasks一次性 script 同 app code 一齊管

🎯 最常考

原則 6(Stateless):session 要放 Redis / DB,process 本身要 stateless 先可以水平 scale — 加多幾隻 instance 都唔會撞 state。

1AWS Landing Zone — 多帳號治理藍圖

Landing Zone 係建構一個符合 AWS Well-Architected 最佳實踐嘅多帳號環境。核心哲學:

  • 帳號分層:唔同 workload 放唔同帳號,故障爆炸半徑隔離
  • 中央管治:統一嘅安全基線、審計、成本控制
  • 標準化供應:新帳號 = 一樣嘅骨架,唔使自己慢慢砌

1.1 帳號結構設計(Organizational Units)

用 AWS Organizations 建立層級式 OU:

Root ├── Security ← Log Archive 帳號 + Security Tooling 帳號 ├── Infrastructure ← 網絡帳號(Transit Gateway、共享服務) └── Workloads ├── Development ├── Staging └── Production
  • 每個 OU 可以套用唔同嘅 SCP 同 guardrails
  • Production 同 Development 徹底隔離,權限同審計強度唔同

1.2 用 AWS Control Tower 起 Landing Zone

AWS Control Tower 係托管嘅 landing zone 服務,自動建立:

  • Management Account — 只做管治,唔放 workload
  • Log Archive 帳號 — 集中收 CloudTrail / Config logs
  • 預設 guardrails + 帳號供應流程(Account Factory)

或者純手動用 Organizations 砌,但 Control Tower 一次過搞掂晒,係 AWS 推薦路徑。

1.3 用戶登入 — IAM Identity Center

  • 前身叫 AWS SSO;single sign-on 所有帳號
  • 支援接返公司 AD / SAML 2.0 federation(混合雲身份)
  • 避免長命 Access Key,支援臨時憑證

1.4 中央審計與安全

服務喺 Landing Zone 嘅角色
CloudTrail全帳號 API 動作記錄 → 去 Log Archive
GuardDuty智能威脅偵測(異常登入、挖礦、port scan)
Security Hub聚合所有安全 findings,單一窗口睇晒
AWS Config全環境資源合規檢查
AWS Budgets成本控制 + 閾值告警

1.5 Guardrails(治理護欄)

  • Preventive(阻止型) = SCP:喺 OU 層直接 deny,例如唔准起喺非指定 region、唔准 public S3、唔准 root 登入
  • Detective(偵察型) = Config rules:偵測違規並告警(例如發現有 public bucket 即刻 alert)

✅ 考試必記 3 點

1. Management Account 唔好放任何 workload,只係管治中樞。
2. SCP 係「頂層限制」:只可以 allow/deny,唔可以 grant 權限;要掛喺 OU 層先對下賬生效。
3. Control Tower guardrails 分 mandatory(強制)同 strongly recommended;SCP 做 preventive、Config 做 detective。
⬆ 回到最頂

2EKS Upgrade — 升級流程與地雷

EKS 升級比其他服務多好多限制,先記硬規則,再講流程。

2.1 硬規則(不可違反)

  • 唔可以跳 minor version:1.29 → 1.30 → 1.31,一次一個,冇得飛
  • Version skew:Node 可以等於或比 Control Plane 舊 最多 1 個 minor version,再舊就入唔到 cluster
  • 支援周期:Standard Support 約 14 個月;可畀錢延長至 Extended Support ~26 個月
  • 冇得 rollback Control Plane:升級唔可以簡單回滾,必須喺 staging 驗證晒先

2.2 升級流程(6 步)

  1. 評估 — 睇 Kubernetes changelog / deprecation:
    • 將被移除嘅舊版 API(例如 `extensions/v1beta1` 系列)
    • CRD / Webhook(Cert-manager、Admission webhooks)有冇新版兼容
    • 用工具掃描:API compatibility checks + kubectl convert
  2. 預先確認 / 升級有相容風險嘅 Add-on — 尤其 VPC CNI(aws-node) 同 CoreDNS,佢哋同 K8s 版本有硬綁定,舊版可能喺升級後出問題
  3. 升 Control Plane — aws eks update-cluster-config 或 Console;EKS 自動 rolling(跨 AZ),期間 API server 短暫唔穩,動作會變慢
  4. 升 Node Group(最關鍵一步)— 逐個 node 做:
    kubectl cordon <node>                 # 標記不可排程
kubectl drain <node> --ignore-daemonsets --delete-emptydir-data  # 逐走 Pod
# Pod 喺其他 healthy node 重新調度
# 更換 / 升級 node,再 uncordon
    • 一定要有 PodDisruptionBudget (PDB),否則一齊 drain 會成堆 Pod 落地
    • 配合 TopologySpreadConstraints / Pod anti-affinity,確保每輪都有足夠副本喺度
  5. 升其餘 Add-on — kube-proxy、EBS/EFS CSI driver 等,對齊最終版本
  6. 驗證 — smoke test、檢查 Terminating / NotReady node、確認 workload 恢復

⚠️ 常見誤解:Add-on「一定最後升」?

唔係。Add-on 同 Control Plane 係「互通相容」關係,冇硬性次序。實務上:
  • VPC CNI / CoreDNS 呢啲有相容風險嘅,反而建議喺升 Control Plane 前/同步就升定
  • 其他 add-on 可以喺 Node Group 之後彈性處理
  • 原則:升之前確認所有 add-on 都支援 target 版本,咁先有序可言

📝 考試焦點

① Node 比 CP 舊多過 1 版 → Node 唔會 join。② 冇 PDB 做 rolling → 服務中斷。③ 唔跳版本 + 14 個月標準支援。④ Add-on 要獨立 trigger,唔會自動跟住升。⑤ 先 staging 後 production。
⬆ 回到最頂

3CloudFormation — 基礎設施即代碼

CloudFormation (CFN) 係 AWS 原生嘅 IaC 工具:用 JSON / YAML template 宣告式建立資源,刪 template = 成批資源一齊刪,唔使自己 click console。

3.1 Template 結構

AWSTemplateFormatVersion: "2010-09-09"
Description: ...
Parameters:      # 部署時傳入嘅可變值(如 CIDR、環境名)
Mappings:        # 環境 → 值嘅對照表(如 env → instance type)
Resources:       # ★ 必填 — 真正會建嘅資源
Outputs:         # 建成後嘅輸出(俾人 / 其他 stack 用)
Metadata:        # 元資料 / 文件說明
Conditions:      # 條件邏輯(如 prod 先行 multi-AZ)

3.2 部署方式

# CLI
aws cloudformation deploy \
  --stack-name my-stack \
  --template-file template.yaml \
  --parameter-overrides Env=prod

# SAM(serverless)
sam build && sam deploy

3.3 關鍵特性

  • 自動 Rollback:任何資源建失敗,自動回滾到上一個健康狀態
  • Change Set:部署前預覽「會新增 / 刪除 / 替換邊啲資源」,唔會直接改嘢,要另外 apply
  • UpdatePolicy:RollingUpdate(逐批)或 Recreate,常配 ASG 用
  • Drift Detection:人手喺 console 改資源但冇經 CFN → 狀態漂移;detect-stack-drift 偵測,但只報告、唔自動修正
  • Nested Stacks:大 stack 內嵌 AWS::CloudFormation::Stack,拆模組重用
  • Cross-stack reference:Outputs + Fn::ImportValue 俾其他 stack 引用
  • Intrinsic Functions:!Ref / !GetAtt / !Sub / !Join / !FindInMap…
  • CreationPolicy / WaitCondition:配 cfn-signal 等 instance「真係 ready」先當建完

3.4 同其他 IaC 工具對比

工具定位特點
CloudFormationAWS 原生 declarative支援所有 AWS 資源、Change Set、Drift
Terraform跨雲 declarativeHCL,要自己管 state
SAMCFN 嘅 serverless 強化自動起 Lambda/API GW/Bucket
CDK用程式碼寫 infraPython/TS/Go 寫,compile 做 CFN template
Elastic BeanstalkPaaS唔算 IaC,可生成 template

⚠️ 考試陷阱

① 刪 stack = 刪晒底層資源;要保留用 DeletionPolicy: Retain(或 Snapshot)。
② Change Set 只係預覽,唔會直接改資源,要另外 apply。
③ Drift 只偵測、唔自動修正。
④ Nested Stack ≠ Cross-stack reference(前者係 stack 嵌 stack,後者係 stack 之間引用)。
⬆ 回到最頂

4SAM — Serverless Application Model

SAM 全名:Serverless Application Model(AWS Serverless Application Model)。

  • 建喺 CloudFormation 之上嘅 serverless 框架
  • 用 AWS::Serverless::* 語法簡化宣告,例如一行 AWS::Serverless::Function 就自動幫你起好 Lambda + IAM Execution Role + Event source 接駁
  • 支援 sam build(本地打包)、sam deploy(部署)、sam local invoke(本地測試)
  • 最終都會轉化成交畀 CloudFormation 落去建
⬆ 回到最頂

5CloudFormation Stack — 部署實例深入

Stack = 一個 template 部署一次嘅「實例」,管理成批資源嘅完整生命周期。

5.1 生命周期狀態

狀態意思
CREATE_IN_PROGRESS / CREATE_COMPLETE建緊 / 建完
CREATE_FAILED / ROLLBACK_COMPLETE建失敗,自動回滾
UPDATE_COMPLETE / UPDATE_ROLLBACK_COMPLETE更新完 / 更新失敗自動回滾
REVIEW_IN_PROGRESS用 Change Set 建立中,未真正 create

5.2 Stack 之間嘅互動

A. Outputs + ImportValue(跨 Stack 引用)

# Stack A
Outputs:
  VpcId:
    Value: !Ref MyVpc
    Export:
      Name: app-vpc-id

# Stack B
Resources:
  Instance:
    Type: AWS::EC2::Instance
    Properties:
      VpcId: !ImportValue app-vpc-id
  • Export 名喺 成個 region 唯一;有人引用緊就刪唔到

B. Nested Stack(Stack 嵌 Stack)

Resources:
  Nested:
    Type: AWS::CloudFormation::Stack
    Properties:
      TemplateURL: https://s3.../nested-template.yaml
      Parameters:
        Cidr: !Ref VpcCidr

一套大 infra 拆多個細 template → 重用 + 分工管理。

5.3 特性

  • 刪 Stack = 資源按依賴倒序刪
  • 想保留資源用 DeletionPolicy: Retain / Snapshot(DB 好常用 Snapshot)
  • CFN 最大好處:冇 state 檔案 — AWS 幫你 track 成個 stack,唔似 Terraform 要自己管理 state(考試愛考)
⬆ 回到最頂

6StackSets — 多帳號 × 多區域部署

StackSets = 用一個 Operation,一次過喺多個帳號 × 多個 Region 部署同一套基建。治管大規模環境嘅神器。

6.1 架構概念

Administration Account └── StackSet (template) ├── Stack Instance → Account A × ap-southeast-1 ├── Stack Instance → Account B × ap-southeast-1 ├── Stack Instance → Account A × us-east-1 └── Stack Instance → Account B × us-east-1
  • 每個「帳號 × 區域」組合係一個 Stack Instance

6.2 權限模型(必記)

  • 跨帳號需要兩個角色:
    • Administration Role(喺 admin 帳號,俾 StackSet assume)
    • Execution Role(喺每個 target 帳號,俾 admin role 去 assume)
  • 利用 Organizations 可以自動信任 + 部署

6.3 兩種類型

Service-managedSelf-managed
帳號管理直接配 Organizations,新帳號自動加入手動指定 target accounts
適用場景推薦(有 Organizations)冇 Organizations / 要精準控制

✅ 重要釐清:單一帳號 × 多 region 要用 StackSet 嗎?

唔一定要。StackSet 嘅核心價值係「跨帳號」一次過管。
淨係「單一帳號 × 多 region」:寫一個 template,喺每個 region 各 deploy 一次(--region us-east-1 / --region ap-southeast-1)就得,簡單直接唔使玩 role 依賴。StackSet 用喺呢度係 overkill。

考試判斷:見到「多帳號跨 region 一次過部署」→ StackSet;淨係「多 region」冇提多帳號 → 普通 stack 分開 deploy。
⬆ 回到最頂

7Route 53 Resolver — Inbound / Outbound

Route 53 Resolver 係處理「VPC ↔ 外面」DNS 互通嘅中間人,三大件:Inbound Endpoint、Outbound Endpoint、Resolver Rules。

7.1 Inbound Resolver(on-prem → 查 VPC 內 DNS)

on-prem DNS client ──(query)──▶ [Inbound Endpoint ENI] ──▶ VPC 內 DNS
  • 讓 on-premise 嘅 DNS resolver 查你 VPC 內部嘅 Private Hosted Zone(例如 example.internal 嘅 RDS / EC2 private DNS name)
  • 係一個 ENI 附喺 VPC 子網;至少開 2 個 subnet 先高可用
  • 用 Security Group 限制邊啲 on-prem 可以 query

7.2 Outbound Resolver(VPC 內 → 查外面 DNS)

VPC 內 instance ──(query)──▶ [Outbound Endpoint] ──▶ on-prem / 自訂 DNS
  • VPC 入面嘅資源想 resolve on-prem 先知嘅域名(例如 corp.internal)
  • 配 Resolver Rules 決定邊啲 domain forward 去邊個 DNS

7.3 對比

InboundOutbound
方向on-prem → 入 VPCVPC → 出外面
解決問題on-prem 查唔到 VPC internal DNSVPC 查唔到 on-prem DNS
例子on-prem connect RDS private nameEC2 call API 用 corp.internal name
形態VPC 內 ENI + SGVPC 內 ENI + SG + forwarding rules

最常見場景:Hybrid DNS 互通(兩個 endpoint 一齊建做雙向)、DR / 多 region 私有 DNS 互通(配合 VPC Peering / Transit Gateway)。

⬆ 回到最頂

8CloudFront Functions — 邊緣超輕量運算

CloudFront Functions 係喺 CloudFront edge 上面行嘅輕量 JavaScript(ES5/ES6 子集),用嚟做 request/response 嘅輕改寫。

8.1 兩個掛鉤點

  • Viewer Request — user request 到達 edge 時
  • Viewer Response — edge 準備好 response 揼返俾 user 前

8.2 特性

  • <1ms 延遲,幾百萬 request 都唔會爆
  • 超平:每百萬 request ~US$0.10(Lambda@Edge 貴好多)
  • 儲存喺 edge,冇 network / IO 存取(純 CPU + header/URL 改動)
  • 分 DEVELOPMENT(測試)同 LIVE(正式)兩個階段

8.3 常用用途

  • URL 改寫 / 重定向
  • Header 修改(CORS、cache-control)
  • JWT / Token 存在性檢查(viewer request 攔截)
  • Geo / Device 分流(睇 Country header)

8.4 CloudFront Functions vs Lambda@Edge

CloudFront FunctionsLambda@Edge
語言JS 子集(ES5)Node / Python 等全語系
事件點得 Viewer Request / ResponseViewer + Origin(更多)
能力極輕量,冇 IO/DB可 IO、DB、動態生成
延遲幾 ms較大
成本平好多貴

📝 考試判斷

只要 Viewer 層輕 transform(改 header、redirect、token check)→ CloudFront Functions。
要 Origin-level 事件 / IO / DB / 大 payload 邏輯 → Lambda@Edge。
⬆ 回到最頂

9AWS Backup — 每日備份 + 加密 EBS

9.1 建立每日備份 Plan

# 1. 開 Backup Vault
aws backup create-backup-vault --backup-vault-name my-vault

# 2. 建 Backup Plan,set 每日 schedule + lifecycle
aws backup create-backup-plan --backup-plan '{
  "BackupPlanName": "daily-ec2",
  "Rules": [{
    "RuleName": "DailyRule",
    "TargetBackupVaultName": "my-vault",
    "ScheduleExpression": "cron(0 2 * * ? *)",
    "StartWindowMinutes": 60,
    "CompletionWindowMinutes": 120,
    "Lifecycle": { "DeleteAfterDays": 30, "MoveToColdStorageAfterDays": 7 }
  }]
}'

# 3. IAM role + tag-based 指派資源(例如 tag: Backup=Daily)

9.2 加密 EBS 嘅處理(重點)

  • AWS Backup 會自動做加密備份,唔使自己額外搞
  • 預設用返原本 EBS 部嗰個 KMS key 加密備份
  • 但如果 Backup Vault 有指定自己嘅 KMS key,會 override 用 vault 個 key

9.3 注意位

  • Cross-region / cross-account copy:用 target 嗰邊嘅 KMS key 重新加密,key 要先喺嗰邊存在
  • Restore 出嚟嘅 EBS 可揀原 key 或改 key
  • KMS key 唔好亂刪 — 刪咗就 restore 唔到!
  • Cross-account 備份要 set 好 KMS key policy / grant
  • 自己管嘅 Customer Managed Key (CMK) 比 default aws/ebs key 更穩陣、可控

✅ 建議架構

CMK 加密 Backup Vault → EC2 tag(Backup:Daily)自動入 plan → Lifecycle 控制成本(Cold Storage + DeleteAfterDays)→ cross-region copy 用 KMS key。新 instance 加 tag 即自動備份,唔使手動 update plan。
⬆ 回到最頂

10IGW vs NAT Gateway — 出網兩條路

10.1 一句分清楚

  • Internet Gateway (IGW) = 全雙工,可以出入兩邊都通,俾 public subnet 直接上網 + 外網連入
  • NAT Gateway (NATGW) = 只出唔入,俾 private subnet 主動出網,但外網入唔到嚟

10.2 Internet Gateway

  • VPC-level 資源,免費
  • 要做安全過濾靠 SG / NACL(IGW 本身冇 filtering)
  • 要 instance 上網:subnet route table 有 0.0.0.0/0 → igw-xxx + instance 有 public IP + SG 允許出站
  • 冇 public IP 嘅 instance 就算有 route 都出入唔到

10.3 NAT Gateway

  • 托管服務,有 Elastic IP,按 小時 + 流量 收費
  • 放喺 public subnet;private subnet 用 route 0.0.0.0/0 → nat-xxx
  • 只撐 outbound:private instance 冇 public IP 都出到網,但外網唔可以主動連入
  • 高可用:NATGW 綁死一個 AZ;多 AZ 嘅話每個 AZ 各自放一個,否則嗰個 AZ 冧機就斷網

10.4 對比表

Internet GatewayNAT Gateway
用途public subnet 出入互聯網private subnet 只出網
方向出入(in/out)只出(outbound)
收費免費EIP + 小時 + 流量
放置VPCpublic subnet
要 public IP?係唔使(private instance)
外網入嚟✅ 可以❌ 唔得

📝 考試場景

EC2 要裝 package / call API 但唔想暴露 → private subnet + NAT Gateway。
Web server / ALB 要接受外網請求 → public subnet + IGW。
多 AZ 高可用 → 每個 AZ 一個 NATGW。
⬆ 回到最頂

11Security Group vs NACL — 兩層防線

11.1 一句分清楚

  • SG = Instance / ENI 級防火牆:有狀態 (stateful)
  • NACL = Subnet 邊界防火牆:無狀態 (stateless)

11.2 Security Group

  • 有狀態:出咗去嘅 request,response 自動 allow,唔使自己寫 inbound return rule
  • 預設 Deny all,只可以寫 Allow(冇得寫 Deny)
  • 可 attach 多部 instance;instance 可掛多個 SG(並集生效)
  • Rule 冇 order,全部一齊 evaluate
  • SG reference:可以引用另一個 SG ID 而唔使寫死 IP(好好用)

11.3 Network ACL

  • 無狀態:inbound 同 outbound 要分開寫,漏寫 return rule 就唔通 ← 最常見考試坑
  • 預設 Allow all;可以寫 Allow 同 Deny
  • 有優先次序:由 number 細嘅 rule 開始,第一條 hit 就採用(precedence)
  • Attach 到 subnet
  • 好處:即時 block IP(黑名單),好啱做 DDoS 防護第一層

11.4 對比表

Security GroupNetwork ACL
層級Instance / ENISubnet
狀態Stateless? 唔係,StatefulStateless
Allow / Deny只 AllowAllow + Deny
Rule 順序冇 order有 number 優先
預設Deny allAllow all

⚠️ 考試陷阱

「返回流量被擋」→ 一定係 NACL 寫漏 outbound rule(SG 唔會犯呢個錯)。
「即時 block IP 做黑名單」→ NACL。
實戰組合:SG 做 instance 層精細控制,NACL 做 subnet 層粗粒度關閘;兩者都要 allow 先放行。
⬆ 回到最頂

12AWS Config vs CloudTrail vs SCP — 三兄弟

12.1 一句分清楚

  • AWS Config = 睇「而家環境符唔符合規矩」:資源 inventory + 合規檢查 + 變更歷史
  • CloudTrail = 睇「邊個喺幾時做咗啲咩」:API 動作日誌
  • SCP = 唔係睇,係管:喺 Organizations 層面限制成員帳號「做得到啲咩」

12.2 AWS Config(狀態 / 合規)

  • 記錄全部資源組態(instance type、tag、SG rules、bucket policy…)+ 變更歷史(Config Timeline)
  • 用 Managed Rules / 自訂 Lambda rule 自動檢查:例如「所有 S3 都要加密」「EC2 要有 tag」「EBS 要 encrypt」
  • 配合 Config Timeline 可以重構「某資源喺某時間係咩樣」→ 事後調查神器

12.3 CloudTrail(動作 / 誰做了什麼)

  • 記錄每個 AWS API call:邊個、幾時、咩 action、對邊個資源、來源 IP
  • Event history 免費 90 日;要長期保留就開 Trail → S3 / CloudWatch
  • 用嚟:forensics、「誰刪咗個 bucket」、合規 audit

12.4 SCP(限權 / 治理)

  • 掛喺 Organizations 嘅 OU / 帳號層級
  • 唔 grant 權限,只 allow + deny;白名單思維
  • 例子:deny ec2:StopInstances 喺 production OU;限制 region;deny root 登入
  • 即使 IAM policy allow,SCP deny 就係 deny

12.5 對比

做啲咩類型層級
CloudTrail記錄 API 動作(邊個做咗咩)監察Account
AWS Config資源狀態 + 合規檢查監察Resource
SCP限制成員帳號能力治理/限制Organizations OU

⚠️ 判斷口訣

「刪咗 S3 bucket 係邊個做」→ CloudTrail(講動作/事件)。
「環境合唔合規、有冇 public bucket、有冇 encrypt」→ AWS Config(講狀態/規則)。
「限制某 OU 唔准開某服務 / root login」→ SCP(講限制/deny)。
詳細到 IAM user 層嘅權限 → IAM policy,唔係 SCP。

13三劍合璧 — Config + CloudTrail + GuardDuty

三樣一齊用先係完整嘅「安全監察 + 合規 + 異常偵測」方案:

13.1 各司其職

服務做咩專攻
CloudTrail記錄所有 API 動作事件 / 動作日誌
AWS Config資源狀態 + 合規環境狀態 / 合規
GuardDuty智能偵測威脅異常異常 + 入侵
口訣:CloudTrail 記「動作」,Config 記「狀態」,GuardDuty 記「壞嘢」。

13.2 成套做法

  1. 中央集中:三個都輸出到中央 Security / Log Archive 帳號(CloudTrail → S3 長期保留)
  2. 聚合:GuardDuty findings + Config 不合規 → 自動聚合上 Security Hub
  3. 告警 / 自動補救:Security Hub + EventBridge → SNS / Lambda 告警;Config Remediation(SSM Automation)自動修正不合規資源
  4. 事後調查:GuardDuty 話你邊個異常 → CloudTrail 循返痕跡 → Config 睇事發時資源狀態 → 完整 timeline
所有帳號 ── CloudTrail / Config / GuardDuty ──▶ 中央 Security/Log Archive 帳號 │ Security Hub(聚合 findings + 合規) │ EventBridge ─┬─ SNS(告警) └─ Lambda(自動補救)

📝 高頻組合題

① GuardDuty 偵測異常 → 背後其實靠 CloudTrail 供應嘅 API 活動數據。
② 檢查「encrypted / public bucket」→ Config;GuardDuty 係睇「陌生 IP 爆破、挖礦、port scan」呢類異常。
③ 三樣都要開晒先有用:CloudTrail 全 region + multi-account;Config 全 region + 揀好 rules;GuardDuty per account 開。
④ 常見 finding type:UnauthorizedAccess:EC2/TorClient、CryptoCurrency:EC2/BitcoinTool。
⬆ 回到最頂

14CloudFormation 卡住 / Timeout 排查

Stack 卡喺 CREATE_IN_PROGRESS / UPDATE_IN_PROGRESS 好耐繼而 timeout,通常唔係即時報錯,而係「靜靜咁等緊啲嘢」。必做第一步:睇 Stack Events。

aws cloudformation describe-stack-events --stack-name my-stack \
  --query "StackEvents[?ResourceStatus=='CREATE_FAILED'||ResourceStatus=='UPDATE_FAILED']"
  • 搵「卡住嗰個資源」+ 佢嘅 Status reason,真相九成喺度

14.1 最常見原因(由熱門排起)

原因點解會卡點查
CreationPolicy / WaitCondition + cfn-signalEC2 冇送「報平安」signal,CFN 一路等到 timeout/var/log/cloud-init-output.log、/var/log/cfn-init.log;user data script 有冇 crash
ASG + ELB health check 唔過instance 一直 unhealthy,等唔到 MinInServiceTarget group health check path/port
Custom Resource(Lambda)timeoutLambda 冇喺限定時間內 send response 俾 CFNLambda timeout 設定 + CloudWatch Logs
IAM / Service Role 權限不足冇權限建資源(偶爾拖到 timeout 先現形)Event 有冇 AccessDenied / not authorized
配額 / 依賴卡住EIP 配額爆、Subnet 冇位、Nested Stack child 卡死檢查配額、child stack 狀態

📝 考試最愛問

「EC2 建嗰陣 stack 卡喺 CREATE_IN_PROGRESS 然後 timeout」→ 十之八九係 cfn-signal 未送到(CreationPolicy/WaitCondition)。答案方向:檢查 user data / cfn-init script、加長 timeout、確保 signal 送達。

15AWS Storage Gateway — 混合雲儲存

Storage Gateway = 連接「on-premises ↔ 雲」嘅儲存橋樑:本地照用標準協定(SMB / NFS / iSCSI / VTL),底層數據其實存喺 AWS。本地睇落似網絡磁碟,實際儲喺雲。

15.1 三種 Gateway

類型協定雲端底層用途
File GatewayNFS / SMBS3(每份檔案 = 一個 object)檔案伺服器上雲、data lake 入口
Volume Gateway — StorediSCSIS3 + EBS snapshot(成個 dataset 喺本地,異步備份)本地大容量 + 雲備份
Volume Gateway — CachediSCSIS3 + EBS snapshot(數據喺雲,本地得 cache)慳本地空間
Tape GatewayiSCSI(VTL 虛擬磁帶庫)S3 / S3 Glacier備份歸檔(Veeam、NetBackup)
(+) FSx File GatewaySMBAmazon FSx for Windows本地快取嘅 FSx 存取

15.2 部署形態

  • 虛擬機:VMware ESXi / Hyper-V / KVM
  • Storage Gateway Hardware Appliance:實體機,俾冇 virtualization 嘅 site

📝 考試選場景

① on-prem file server 上雲但唔想改 SMB/NFS → File Gateway。
② 完整 dataset 要喺本地 + 異步備份上雲 → Volume Gateway(Stored)。
③ 本地空間有限,熱數據快、冷數據上雲 → Volume Gateway(Cached)。
④ tape backup 軟件無痛轉 S3/Glacier → Tape Gateway。
⬆ 回到最頂

16EC2 可以用 Storage Gateway 嗎?

EC2 自己嘅硬盤用 EBS,唔需要 Storage Gateway —— 後者係為 on-premises 設計。但有三種情況會扯上關係:

  • Gateway 本身行喺 EC2:AWS 提供 Storage Gateway AMI,可以直接開 EC2 instance 做 gateway(測試 / 雲端 file gateway pattern 常見)
  • EC2 mount File Gateway 嘅 share:可行但好少用 —— EC2 直接 S3 SDK / EFS 更簡單
  • 備份 target:EC2 嘅備份軟件寫入 Tape Gateway VTL → S3/Glacier
EC2 儲存需求應該用
系統盤 / 區塊存儲EBS
共享檔案系統EFS(Linux)/ FSx(Windows)
大容量物件儲存S3
高吞吐暫存Instance Store / EBS io2
Hybrid 橋樑Storage Gateway(通常配 on-prem)

⚠️ 考試判斷

「EC2 用 Storage Gateway 代替 EBS」係錯誤選項。Storage Gateway 係 hybrid(雲+本地)架構用;純雲環境唔需要佢。

17Secrets Manager vs SSM Parameter Store

Secrets Manager = 為「會流動嘅 secrets」設計(自動輪換);Parameter Store = 輕量「設定 + secrets」雜物櫃(基本免費)。

17.1 Secrets Manager

  • 自動 Rotation(輪換):Lambda + 內建 rotation,原生支援 RDS / Redshift / DocumentDB 等 → 招牌功能
  • Multi-Region replica:secret 一鍵同步多 region
  • CloudTrail 記錄到 secret 級 + 刪除有 7-30 日 recovery window
  • 收費:每個 secret ~$0.4/月 + API call;上限 64 KB

17.2 SSM Parameter Store

  • 係 AWS Systems Manager 嘅功能,唔係獨立服務
  • String / StringList / SecureString(KMS 加密)
  • 分層路徑:/prod/rds/password、/dev/rds/password,按 path 管理
  • Standard 免費(4KB);Advanced(8KB、policy)先收費
  • 冇內建 rotation(要自己 Lambda + EventBridge);冇 recovery window

17.3 對比 + 選擇口訣

Secrets ManagerParameter Store
自動 rotation✅ 內建❌ 自己搞
收費💵 按 secret + API✅ Standard 免費
最大 size64 KB4KB / 8KB(Advanced)
多 region 同步✅❌
刪除恢復✅ 7-30 日❌
分層路徑❌✅

✅ 口訣

「要自動輪換 DB 密碼」→ Secrets Manager。「要免費存環境設定 / AMI ID / 細 secrets」→ Parameter Store。「跨 region 同步 / 怕誤刪 / 要 audit」→ Secrets Manager。兩者都用 KMS 加密(SecureString / secrets 內容)。

18AWS DataSync — 數據搬運工

DataSync 係 AWS 托管嘅數據傳輸 / 同步服務:on-prem ↔ AWS,或者 AWS 服務之間。佢唔係存取服務,係「傳輸任務」 —— 搬完就走。

18.1 點運作

on-prem NFS/SMB ──(DataSync Agent VM)──▶ S3 / EFS / FSx / 另一邊 on-prem
  • 喺 on-prem 起個 DataSync Agent(VMware / Hyper-V / KVM VM)
  • Agent 讀 NFS/SMB share → 傳去 S3、EFS、FSx(Lustre / Windows / OpenZFS / ONTAP)
  • 全程 TLS 加密,傳完做 checksum 驗證

18.2 招牌功能

  • 增量同步:第一次全量,之後淨係傳改咗嘅檔案
  • 排程(schedule)+ 頻寬限制(限速,唔影響生產網絡)
  • 過濾規則(include / exclude 檔案)
  • 保留 metadata / POSIX 權限 / 時間戳
  • 並行多線程,速度快過人手 rsync

18.3 用途

  • 一次性搬上雲(migration)
  • 持續同步(on-prem → S3 / EFS / FSx 做 DR 複製)
  • 檔案伺服器遷移去 S3 / EFS / FSx

18.4 DataSync vs Storage Gateway(愛考!)

DataSyncStorage Gateway
性質傳輸任務(搬完就走)持續存取橋樑(長期掛載)
用途一次性 / 週期性搬資料on-prem 應用照常用 NFS/SMB/iSCSI
介面唔會長期提供掛載SMB / NFS / iSCSI / VTL
例子公司 5TB 檔案搬去 S3file server 每日照用,底層喺 S3

📝 考試判斷

「搬資料(migration / 同步)」→ DataSync。「on-prem 要照常用 NFS/SMB/iSCSI 存取」→ Storage Gateway。

19Amazon FSx — 托管檔案系統家族

FSx 係一系列托管檔案系統,每個針對唔同 workload;DataSync 通常就係用嚟將 on-prem 檔案搬入 FSx。

19.1 四款 FSx

類型協定適合特色
FSx for Windows File ServerSMBWindows 應用、SQL Server、AD 環境Active Directory 整合、VSS shadow copies、DFS、配額
FSx for LustrePOSIXHPC / AI / ML 訓練百萬 IOPS 級、可連 S3 data repository 同步訓練數據
FSx for OpenZFSNFSLinux、通用企業ZFS snapshots / clones,慳儲存
FSx for NetApp ONTAPNFS / SMB / iSCSI由 on-prem NetApp 遷移SnapMirror、FlexVol、企業 NAS 功能

19.2 考試選擇題要點

  • Windows + AD + SMB → FSx for Windows File Server(唔係 EFS!)
  • HPC / ML 訓練數據,高吞吐,要連 S3 → FSx for Lustre
  • 由 NetApp 搬過嚟,要保留 SnapMirror → FSx for NetApp ONTAP
  • Linux 通用 POSIX → EFS(FSx 家族以外嘅基本答案)

19.3 DataSync + FSx 組合(標準 migration pattern)

on-prem file server ──(DataSync Agent)──▶ FSx for Windows / Lustre / OpenZFS / ONTAP
  • DataSync 負責搬,FSx 負責搬完之後畀應用用

✅ EFS vs FSx 一句記

EFS = AWS 自家 Linux NFS,通用、簡單、auto-scaling。FSx = 四款特化檔案系統(Windows / Lustre / OpenZFS / ONTAP),要 AD、HPC、企業 NAS 功能先揀佢。

19.4 FSx for Windows 深入

功能有咩用
SMB 3.0 / 3.1.1Windows 原生協定,支援 SMB Multichannel(多路徑加速)
VSS Shadow Copies用戶自己「還原上一版」,唔使 IT 出手
DFS Namespaces / Replication分散式檔案名空間 + 複製
NTFS ACLs + Quotas精細權限 + 容量配額
AD 整合Kerberos 認證、AD 用戶 / 群組權限
  • 部署選項:Single-AZ(平,測試用)vs Multi-AZ(跨 AZ 自動 failover,生產必用)
  • Storage:SSD(低延遲)/ HDD(慳錢,throughput-optimized)
  • Backup:每日自動備份 + 手動 snapshot,支援 VSS-consistent(應用一致)

19.5 同 AD 做 Integration(重點)

  • 支援邊啲 AD?

    • 自家 on-prem AD / 其它 AD —— 用 AD Connector 或 VPN / Direct Connect 打通
  • 點 join(流程):建立 FSx 時揀 Active Directory → FSx 用 service account / delegated admin 加入 domain → 變成 domain member → 喺 AD 開 users/groups → 設 share 權限 + NTFS ACLs
  • 用戶點存取:EC2(已 join AD)或 on-prem 機(VPN/DX)用 AD 帳號經 SMB mount → Kerberos 認證 → NTFS ACL 檢查;權限跟 AD group 走

  • Security:傳輸 SMB 3.0 加密、靜態 KMS 加密、Security Group 限存取;FSx 喺 VPC 內唔好開 public

19.6 家族同 AD 嘅關係

FSx 類型接 AD?詳情

FSx for NetApp ONTAP✅ 支援SMB 用 AD/Kerberos;NFS 可用 LDAP

📝 FSx 考試陷阱

① Windows 應用 + AD 用戶 + SMB → FSx for Windows(配 AWS Managed Microsoft AD)。
② 要 VSS / DFS / NTFS ACL → FSx for Windows。
③ 精細權限 → AD 授權模式;用 IAM 控制 → IAM 授權模式。
④ 生產高可用 → Multi-AZ。
⑤ HPC 高吞吐 → Lustre(唔好揀 FSx for Windows!)。
⑥ on-prem AD → AD Connector 或 VPN/DX 打通。

20AWS Directory Service — AD 三兄弟

一句分清楚:

  • Managed Microsoft AD = AWS 幫你起一個真正嘅 AD domain controller(自己有一套)
  • AD Connector = 唔起 AD,淨係「轉接器」連返你 on-prem 嘅 AD
  • Simple AD = 輕量獨立 AD(Linux 用 Samba),功能少啲

20.1 AWS Managed Microsoft AD

  • AWS 托管一對 Microsoft AD domain controllers(至少 2 個 AZ,高可用)
  • 真 Microsoft AD:Kerberos、NTLM、LDAP、Group Policy、trust relationships、FSMO
  • 可同 on-prem AD 做 one-way / two-way forest trust
  • 內建 SSO + MFA(配 IAM Identity Center);按小時收費
  • 適合:冇自己 AD / 想喺雲上起正式 AD + Group Policy / trust

20.2 AD Connector

  • 唔起 domain controller,淨係 proxy / gateway 指向 on-prem AD
  • on-prem AD 係唯一權威;AWS 資源(EC2 join domain、FSx、WorkSpaces)經 connector 認證
  • 冇 Group Policy / trust / MFA 呢啲 AD server 功能
  • 適合:已經有 on-prem AD,想 AWS 資源直接用返,唔想複製

20.3 Simple AD

  • 用 Samba 4 起嘅輕量目錄(唔係真 Microsoft AD)
  • 支援基本 LDAP、Kerberos、user/group;GPO 有限度
  • 唔支援:trust relationships、完整 AD 管理工具
  • 最平(Small 500 users / Large 5,000 users);適合測試 / 細規模,唔好做 production

20.4 對比表

Managed Microsoft ADAD ConnectorSimple AD
本質真 Microsoft AD(托管 DC)轉接器(連 on-prem)Samba 輕量 AD
有冇自己 DC✅ 有(2+ AZ)❌ 冇✅ 有(輕量)
要 on-prem AD?唔使(可 trust)要(先有用)唔使
Group Policy✅❌⚠️ 有限
Trust✅ one/two-way❌❌
MFA / SSO✅ 內建❌❌
價錢最貴中等最平
適合雲上正式 AD已有 on-prem AD測試 / 細規模

📝 考試場景

① 公司已有 on-prem AD,想 AWS 資源用返嗰啲帳號 → AD Connector。
② 冇 AD,想雲上正式 Microsoft AD(Group Policy / trust)→ Managed Microsoft AD。
③ 測試環境要平嘅 AD 兼容目錄 → Simple AD。
④ FSx for Windows join domain → 配 Managed Microsoft AD(雲內)或 AD Connector(on-prem)。
⑤ 要 one-way trust 單一登入 → Managed Microsoft AD(trust 只有佢支援)。

⚠️ 陷阱

① AD Connector 唔係 directory 本身 —— 冇咗 on-prem AD 就冇嘢可用。
② Simple AD 唔支援 trust / 完整 GPO,唔好見「AD」就以為乜都得。
③ Managed Microsoft AD 按小時收費,長期行要計成本。
④ 全部喺 VPC 內起,出唔到 public。
